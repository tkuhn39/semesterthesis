## ADR-101 — Restart as a layered domain library with staged, adversarially gated increments (2026-09-28)

**Context.** The legacy workbench (FastAPI + Next.js, ~22k LOC backend, 268 tests) accumulated 65 open
adversarial findings (2026-09-09 audit), among them core-math defects: three unguarded inverse-involute
implementations, steel formulas applied to plastic, crashes at boundary inputs, `acos` clamping. Root
cause: features were added faster than they were adversarially verified. Deadline in a few weeks.

**Decision.**
1. The legacy tree is archived read-only and unversioned under
   `30_references_and_examples/38_legacy_workbench/` (git tag `legacy-workbench-final` = 4af1d2b keeps the
   history). It may be read as a design reference; importing or reviving it is forbidden (ruff ban on `app`).
2. The new toolchain is a **domain library first**: package `gearcore` (`20_code/10_gearcore`, src layout,
   pydantic contracts, pure functions, no process state). API (`20_api`), Docker (`30_docker`) and UI
   (`40_ui`) come later as thin wrappers over the same contracts.
3. Work proceeds in **small increments**, each = module + tests (unit, property-based, fixture parity) +
   notebook section + **adversarial gate** by a read-only reviewer agent (protocol in
   `adversarial_gate.md`). The next increment starts only when P0 = 0 and every P1 is fixed or entered in
   `known_limits.md` with a reason.
4. Stage 1 scope: 2D geometry chain for external spur **and helical** gears generated by rack-type tools
   (involute/basic rack → pair geometry → tool-based generation incl. trochoid root and transverse contour →
   inspection dimensions → allowances/tolerances → synthesis). Internal gears, rack as a mating element,
   shaper/profile tools, second tool and protuberance flank are prepared extension points
   (`extension_points.md`) that raise `NotSupportedError` today.
5. Steel/plastic dispatch (`MaterialKind`, required, no default) and the material database contract are
   part of the foundation; their contents are stage 2.

**Consequences.** Slower first visible progress, but every shipped formula is traceable and adversarially
checked; the thesis gets a verified base and a documented norm comparison. Legacy features (variation,
FE deck, UI) return only when rebuilt on the new contracts.

## ADR-102 — STplus as numeric oracle: batch runs, fixtures with provenance and trust levels (2026-09-28)

**Context.** FVA STplus 11.1F (FZG research software, local installation under
`30_references_and_examples/33_STplus/STplus11-1F/`, git-ignored) computes geometry per DIN 3960:1987
tool-based and can export the transverse tooth contour as point lists. Neither DIN ISO 21771 nor DIN 21773
contain complete numerical examples; ISO/TR 6336-30 provides worked examples for load capacity with some
geometry values.

**Decision.** `scripts/stplus_oracle.py` (Windows only, never in CI) runs the exe in batch mode
(`STplus.exe --CFG <cfg>`, contour export via `STIRNKOORD_EIN_WKZ`, `PLOT_VERZAHNUNG_W1`,
`PLOTGENAUIGKEIT`, `Pfad_Meldungsausgabe`) in a scratch directory and stores per case
`input.ste`, `report.sta.txt`, `geometry.json`, `contour_wz1.json`, `contour_wz2.json`, `meta.json`
(STplus version from the report header, run date, SHA-256 of the input, settings) under
`src/gearcore/data/stplus/<case>/`. Reference pairs supplied by the user (`33_STplus/*.ste/.sta`,
`33_STplus/weitere_Konfigurationen/`) are imported without a rerun and carry a **trust level**:
kst-E and kst-B `verified`, kst-A and kst-C `unverified` (user statement 2026-09-28); unverified pairs only
warn in parity tests and are additionally re-run with 11.1F to expose input errors or version drift.
Parity tests compare every mapped `.sta` symbol within a unit-based tolerance **or** an entry in
`expected_differences.yaml` (see ADR-105). The exe, its databases and the manual never enter git, CI or
containers; the repo is private, so raw listings may be committed as `report.sta.txt` (`*.sta` is
git-ignored repo-wide).

**Consequences.** Every geometry quantity of the DIN 3960 chain and the sampled contour can be checked
differentially against the institute's tool for any input; CI/Linux never need the exe.

**Findings of the first runs (2026-09-28, STplus 11.1F):**
- The exe opens its runtime companions (`debug.dbe`, `DEFAULT.STY`) relative to the working
  directory (`IMELIB: IOSTAT = 29`); the oracle copies them into the scratch directory so `bin/`
  stays untouched. `Zuordnungsdatei = qelesed.stq` may be absent without effect.
- Config and input must be CRLF with a single CR; Windows text mode doubled the CR (`\r\r\n`) and
  STplus took the stray CR as part of the output file name (`IOSTAT = 43`).
- `Pfad_Meldungsausgabe` works: contour files land in the scratch directory, nothing in `bin/`.
- Contour export grammar: `x ; y` per line (mm, scientific notation), one tooth centred on +y from
  root circle to root circle (fzg_c: r_min = d_f/2, r_max = d_a/2 to 0.1 µm).
- STplus also writes the interface file `ausgabe.sts` (manual §6.2): every result as
  `KEY = values` with ten significant digits, same grammar as `.ste`. It is stored as
  `interface.sts.txt`/`interface.json` and is the preferred parity reference for own runs (the
  `.sta` listing prints three decimals).
- Supplied listings vs 11.1F re-runs of the same inputs: kst-E (11.0F), kst-B (9.0F) and kst-C
  (9.0F) reproduce every geometry value; kst-A (6.0.9) differs only in `d_Fs-n` (not computed by
  6.0) and one rounding digit of the chordal thickness. The trust levels stay as the user stated
  them (they concern the inputs, not the computation).

## ADR-103 — Equation traceability (`@eq`) and verified source registry (2026-09-28)

**Decision.** `gearcore.trace.eq(source, eq, *, section, page, note)` records, without wrapping the
function, which equation of which source (key = norm number **and edition**, e.g. `ISO21771:2014`) a
function realises; stacked decorators are allowed. Tests link via `@pytest.mark.eq(source, eq)`.
`scripts/build_traceability.py` renders `traceability.md` (source | eq | §/page | function | tests |
notebooks | status). `data/sources.yaml` lists every source with identifier (norm edition, DOI, ISBN-13,
patent number, FVA Heft) and an explicit `verified {method, by, date}` block; `scripts/verify_sources.py`
resolves DOIs via Crossref and checks ISBN checksums, printing the comparison for the user — it never
writes automatically. `test_trace.py` fails on unknown source keys and on public computational functions
without `@eq`. No norm text is reproduced; formulas are transcribed in own LaTeX.

**Consequences.** Every formula in code and every citation in the thesis can be checked back to a page of
a primary source; fabricated references cannot enter the registry unnoticed.

## ADR-104 — Notebooks are executable norm documentation, never the implementation (2026-09-28)

**Decision.** `40_jupyter-notebooks/` holds one notebook per norm chapter (German prose, English code)
following the template: goal → norm reference (edition, §, eq., page) → own LaTeX transcription →
`gearcore` call → worked example against norm example and STplus fixture → `assert` with the fixture
tolerance → plot. Notebooks run in CI (`pytest --nbmake`); outputs are stripped on commit
(`nbstripout`); `test_notebooks_are_documentation.py` (nbformat + `ast`) fails when a notebook defines
formula code outside plotting helpers. Alternatives rejected: notebooks as implementation (untestable,
undiffable, invites formula duplication — the legacy failure mode) and Markdown only (not executable).

## ADR-105 — Current norm wins; deviations from STplus's norms are a documented deliverable (2026-09-28)

**Context.** STplus prints "Geometrieberechnung nach DIN 3960 (März 1987)" and uses DIN 3961/62/63,
DIN 3967, DIN 3964 (1978/80). DIN 3960 is withdrawn (successors DIN ISO 21771:2014-08, DIN 21772:2012-07 →
DIN ISO 1328-1:2018-03, DIN 21773:2014-08). The thesis must state what changed.

**Decision.** The newest valid norm is the computational basis (DIN ISO 21771:2014 incl. Annex NB
corrections, DIN 21773:2014, DIN 3967:1978, DIN 3964:1980, DIN 867:1986, ISO 53:1998, DIN 3972:1952,
DIN ISO 1328-1:2018/-2:2021; later ISO 6336:2019 family, ISO/TS 6336-20/-21/-22, VDI 2736). Where the
current norm and the STplus chain differ, the difference is entered in `expected_differences.yaml`
(old {source, eq, section}, new {source, eq, section}, reason, numeric example, effect) and rendered to
`norm_differences.md` (German, thesis-ready). Correct current-norm code is never changed to match the
oracle. Items STplus prints without a current-norm home (Lewis parabola, K*/U factor, FVA-166 losses,
CCS 1996) are left out.
